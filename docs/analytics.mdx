# Analytics

Three separate things get called "analytics" here, and conflating them is how a
privacy rule gets broken by accident. They are:

| | What it answers | Who may see it | Where it lives |
|---|---|---|---|
| **Owner insights** | "How is MY listing doing?" | The owner, authenticated | `GET /api/analytics` |
| **Marketplace aggregates** | "What does this market look like?" | Anyone, public | `GET /api/analytics/stats` |
| **Product observability** | "Did location selection work?" | Homiio's own logs | `POST /api/observability/events` |

The first two are computed from Homiio's own PostgreSQL rows. The third is a
different kind of thing entirely: a versioned event stream about whether the
product *works*, deliberately built so it cannot carry an address.

**There is no third-party analytics SDK in this repository.** No PostHog, no
Mixpanel, no Amplitude, no Segment, on web or native. Nothing about a user's IP,
fingerprint or session leaves the device to a vendor. Verify rather than trust
this paragraph:

```bash
grep -rniE 'posthog|mixpanel|amplitude|@segment/' packages/ --include=package.json
```

Adding one is not a dependency decision — it needs an explicit privacy review
against [ADR 0003](./adr/0003-privacy-verification-publication.md).

## Owner insights — `GET /api/analytics`

Authenticated. Returns what the calling owner's own listings did over a period,
computed from real rows in `recently_viewed`, `saved_items` and
`viewing_requests`. `?period=` accepts `7d`, `30d` or `90d` and defaults to
`30d`.

```ts
{
  period: '7d' | '30d' | '90d';
  totalInteractions: number;
  properties: { listed: number };
  views: { total: number; uniqueViewers: number };
  saves: { total: number };
  viewingRequests: {
    received: number; pending: number;
    approved: number; declined: number; cancelled: number;
  };
  insights: string[];   // plain sentences, generated only when the count is > 0
}
```

A caller with no Homiio profile gets the same shape with every figure at zero,
not a 404 — the screen renders an empty state rather than an error.

**Metrics with no backing data are returned as `0`. Nothing is fabricated and
nothing is extrapolated.** That rule is worth stating because this endpoint used
to violate it in the other direction: it delegated to an optional cross-app
service and, when that was absent, returned a plausible-looking "fallback"
payload with invented revenue and satisfaction trends. Those numbers described
nothing. A zero that means zero is more useful than a number that means nothing.

The port also fixed two silent defects worth knowing about if you are reading old
dashboards: owned listings were being selected by a field the schema did not
declare, so the set was always empty and every figure was 0 regardless of
activity; and `uniqueSavers` counted a column that did not exist. Both now count
`oxy_user_id`, which is the real owner key.

## Marketplace aggregates — `GET /api/analytics/stats`

Public, mounted on `routes/public.ts`. Five aggregates run in parallel against
PostgreSQL:

```ts
const [catalogue, appSaves, pricing, topCities, priceBuckets] = await Promise.all([
  countAppWideCatalogue(getDb()),
  countAppWideSaves(getDb()),
  summarizeCatalogueRent(getDb()),
  findTopCitiesByListings(getDb(), TOP_CITIES_LIMIT),
  countListingsByPriceBucket(getDb(), PRICE_BUCKET_BOUNDARIES),
]);
```

They live in `packages/backend/db/analytics/ownerAnalytics.ts`, not inline in the
controller. Response:

```ts
interface AppStats {
  totals:  { properties: number; cities: number; saves: number; uniqueSavers: number };
  pricing: { averageRent: number; minRent: number; maxRent: number };
  topCities: { cityId: string; city: string; state: string; properties: number; averageRent: number }[];
  priceBuckets: { bucket: string; count: number }[];
}
```

The price histogram uses fixed monthly-rent boundaries — `0, 500, 1000, 1500,
2000, 3000, 5000, 10000` — implemented with `width_bucket`. Bands are numbered
from 1 and anything at or above the last boundary lands in a `10000+` overflow
band; a band nobody's listing falls into is **absent** from the response rather
than present with a zero. Consumers must not assume every band appears.

`topCities` returns a `cityId` alongside the display name, so a caller can link
to the city rather than re-resolving a name into an id — the kind of round trip
that produces the wrong Barcelona.

Everything on this endpoint is marketplace-level. No per-user information leaves
the server, by construction rather than by filtering: none of the five aggregates
selects a user column.

## Product observability — `POST /api/observability/events`

This is the newest surface and the least like the other two. It answers "does the
product work" — did the location permission resolve, did the geocoder fall back,
did a search return nothing, did somebody abandon the review wizard at step
four — and it is engineered so that it **cannot carry an address**.

- **Public and unauthenticated, deliberately.** The most important events happen
  before anybody signs in: the first-open permission prompt, the first search,
  the fallback after a geocoder failure. Requiring a session would leave exactly
  the cold-start path this exists to observe unobserved. Nothing in the handler
  reads `req.user`.
- **It always answers `202`.** A telemetry endpoint that returns 4xx or 5xx
  teaches a client to retry, and a retry loop driven by telemetry is a
  self-inflicted outage. The body reports what was accepted and what was refused;
  the status never carries that information.
- **The sink is the structured logger**, not a table. That is a ceiling on
  purpose: a table would make this a business-intelligence system, which is out
  of scope, and it would make retention a per-event policy nobody maintains.
  As a log group, retention is one setting owned by `oxy-infra`.

The event vocabulary is versioned (`OBSERVABILITY_SCHEMA_VERSION`) and closed —
thirteen names today, including `location_permission_resolved`,
`location_selection_committed`, `geocoder_request_completed`, `search_submitted`,
`map_area_search_committed`, `search_results_loaded`, `search_zero_results`,
`address_candidate_selected`, `review_step_completed` and `review_abandoned`.
Read `packages/shared-types/src/observability/schema.ts` for the current set;
an event name not in it is refused.

### The prohibition on geographic PII

**No event may carry a coordinate, an address, a postcode, a street, a listing's
exact position, or anything from which one can be reconstructed.** This is not a
review convention — it is enforced in code and it is enforced on both sides.

The mechanism is *bucketing*: a value that would identify a place is replaced by
a band before it is ever an event field. Radius becomes a radius bucket, a result
count becomes a count bucket, a map viewport becomes an area bucket and a zoom
bucket, a latency becomes a latency bucket, a free-text query becomes a length
bucket. `location.kind` records that a query was scoped to a `city`, a `bbox` or
a `radius` — never to *which* one, at coordinate precision.

`redactObservabilityEvent` in `@homiio/shared-types` is the single
implementation, and it runs **twice**: the client redacts before sending, and the
server redacts again on ingest. The second pass is not paranoia about our own
code — an old build, a modified build, or something that is not our client at all
reaches the same public route, so the server cannot treat a client-side pass as
having happened.

Two properties of the ingest path that are easy to get backwards:

- It **preserves** the client's `surface` and `occurredAt`. A phone's event
  relabelled `server` is a lie about where it happened.
- It does **not** sample. The client already did; sampling twice silently squares
  the rate.

The classification rules these enforce are
[ADR 0003](./adr/0003-privacy-verification-publication.md) — the four-tier data
classification, the precision ladder, and the k-anonymity floor that any
aggregate must clear before publication. Do not restate them; that ADR is the
authority, and an aggregate published without checking it against the floor is
the failure mode this whole pipeline exists to avoid.
