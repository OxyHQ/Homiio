# Homiio

Homiio is the housing trust and transparency layer: find a place, research its history, learn what it really costs, understand what living there was like, and manage or defend the tenancy. The frontend is a single Expo / React Native codebase targeting iOS, Android and Web. The backend is a Node + Express API on PostgreSQL with PostGIS, plus Stripe for subscriptions, AWS S3 + Sharp for media, and **Sindi**, the in-app tenant-rights assistant powered by Alia.

## What it is

More than a listings marketplace, and the difference is structural rather than aspirational:

- **A dwelling is permanent; a listing is temporary.** A listing is a sourced advertisement pointing at a physical place. Reviews, rent history and eviction records attach to the *place*, so they outlive the advert. See the [Glossary](./glossary) and [ADR 0001](./adr/0001-canonical-housing-graph).
- **Location is never implicit.** Every surface that answers "where?" says which area it is querying, free text and geographic scope are separate dimensions, and a geocoding failure is a visible error rather than a silent worldwide feed. [ADR 0002](./adr/0002-location-and-search-contract).
- **Privacy by precision.** An address, a coordinate and a review are stored at one precision and published at a coarser one, decided by audience rather than by whichever serializer runs. [ADR 0003](./adr/0003-privacy-verification-publication).
- **Prices must be explainable.** Local, versioned, with their reasoning and confidence — never one universal score. [ADR 0004](./adr/0004-local-explainable-pricing).
- **Moderation is communal.** No admin panel, no moderator queue, no privileged action over user content. That is a product decision, not a gap.
- **Beyond rentals.** `PropertyType` covers couchsurfing, co-living, hostels, guesthouses, campsites, boats, treehouses and yurts, each with `accommodationDetails` for sleeping arrangement, host preferences, languages and meals.
- **Identity via Oxy.** Sign-in, account switching and avatars come from `@oxyhq/services`. Homiio stores no passwords.

The four records above are **Proposed**: they bind design, and they are not all shipped. Where this documentation describes a target it says so.

Inside the repo:

| Package | Role |
|---------|------|
| `frontend` (`@homiio/frontend`) | Expo Router app. NativeWind + Tailwind for styling, Zustand for local state, TanStack Query for server state, `@oxyhq/bloom` for primitives. |
| `backend` (`@homiio/backend`) | Express 4 + drizzle-orm (PostgreSQL + PostGIS) API, plus a separate worker process. Stripe billing, Sharp + S3 image pipeline, BullMQ ingestion, AI SDK streaming endpoints. |
| `listing-providers` (`@homiio/listing-providers`) | The provider plugin contract, the shared fetch runtime, and the portal plugins. Consumed by the worker. |
| `shared-types` (`@homiio/shared-types`) | Pure TypeScript — the entity DTOs, the `format/` money/unit/date module, and the observability event schema. Built first via `postinstall`. |

## Architecture

```
   ┌──────────────────────┐                  ┌──────────────────────┐
   │   Homiio Frontend    │  ── REST ─────▶  │   Homiio Backend     │
   │   (Expo / RN / Web)  │                  │  (Express + Postgres)│
   │                      │  ◀── AI stream ─ │                      │
   └──────────────────────┘                  └──────────────────────┘
            │                                          │
            ▼                                          ▼
     @oxyhq/services                           Stripe + S3 + Alia + Oxy inference
     (auth, account switcher)                  + Oxy API (identity)
                                                       │
                                                       ▼
                                                 PostgreSQL
                                        (Property, Profile, Billing, Lease,
                                         City, Address, Review, Conversation)
```

Build order matters: `@homiio/shared-types` is built ahead of the others via a root `postinstall`, then `frontend` and `backend` can build in parallel.

## Install

```sh
git clone https://github.com/OxyHQ/Homiio.git
cd Homiio
bun install
```

`bun install` resolves all three workspaces and runs `bun run build:shared-types` automatically as `postinstall`.

### Prerequisites

- Node.js 22.x (pinned in `engines`)
- Bun 1.0+
- PostgreSQL with PostGIS (local or hosted)
- For iOS: macOS + Xcode. For Android: Android Studio.

## Core concepts

### Listings and places

A listing (`Property`) is an advertisement; the place it points at is an `addresses` row, and only the place is permanent. A listing carries `id`, an `address`, and **`offerings`** — the single source of truth for how it is offered:

```ts
offerings: OfferingType[];        // long_term_rent | short_term_rent | sale | exchange
longTermRent?: LongTermRent;      // present iff offerings includes LONG_TERM_RENT — monthlyAmount
shortTermRent?: ShortTermRent;    // present iff offerings includes SHORT_TERM_RENT — nightlyRate
sale?: PropertySale;              // present iff offerings includes SALE — price
exchange?: PropertyExchange;      // present iff offerings includes EXCHANGE — swap | host | both
```

The server validates that `offerings` **exactly equals** the set of priced blocks present, and each block's unit is fixed: monthly is always monthly, nightly always nightly, whatever the browse mode.

A listing is either first-party (`oxyUserId` set) or external (`isExternal: true`, no owner, mandatory `sourceUrl`, an `expires_at` deadline reaped by the expiry sweep). External listings are visibly marked and cannot be applied to or booked in-app.

See [Listings](./listings) for the full DTO, the address relation, the filters and external ingest.

### Profiles, not users

Homiio sits behind Oxy identity. Each Oxy user gets one or more **profiles** (Personal, Agency, Business, Cooperative). Personal profiles include an auto-calculated trust score from profile completion, verification status, rental history, and references.

The frontend's `ProfileProvider` loads profiles immediately after `useOxy()` reports authentication; the backend's `getOrCreateActiveProfile` endpoint creates a default Personal profile on first sign-in. There's no separate "create your account" step — profile creation is transparent.

### Sindi (AI tenant-rights assistant)

Sindi is the in-app AI assistant and a provisioned Alia agent backed by its canonical bot account. Its interactive, persisted chat route sends that `SINDI_ALIA_AGENT_ID` to the Alia API with the already-authenticated user's Oxy token, so Alia remains the owner of the agent, chat, tools and memory before it reaches Kaana. This repository deliberately does not create or guess the bot account or agent id. Homiio's one-shot features — conversation titles, filter extraction, smart suggestions, and contract or image analysis — call the Oxy inference edge with Homiio's service identity and an Oxy-owned routing profile. Homiio never calls Kaana or an upstream provider directly, and never constructs Kaana's `authorizedRoutes`; Oxy resolves policy and the signed data-plane envelope for those point requests.

`@oxyhq/core` currently exposes only non-streaming `respond()`. Homiio therefore preserves the frontend's AI Data Stream wire format by returning the completed response as one buffered text frame. True token streaming remains blocked on a published Oxy SDK streaming method; this adapter must be removed in the same change that adopts that method.

The system prompt is explicit:

> You are Sindi, an AI tenant-rights assistant for Homiio. Be concise, accurate, and pro-tenant. Prioritize tenant rights, fair housing, and current local law. Search Homiio properties first when asked for places to rent; then add rights tips. Prefer official sources and Sindicat de Llogateres for Catalonia queries.

When the user asks Sindi for listings, it can embed a machine-readable property block at the end of its reply:

```
<PROPERTIES_JSON>["propertyId1","propertyId2","propertyId3"]</PROPERTIES_JSON>
```

The frontend parses that tag and renders inline property cards under Sindi's message. Conversations are persisted as rows in PostgreSQL.

### Stripe billing (Homiio+ / file credits / Founder)

Three products are wired through Stripe Checkout:

| Product | Mode | Effect |
|---------|------|--------|
| `plus` | `subscription` | Sets `Billing.plusActive: true`, unlocks unlimited contract reviews and premium features. |
| `file` | `payment` | One-off, increments `Billing.fileCredits` by 1. |
| `founder` | `subscription` | Sets `Billing.founderSupporter: true` — supporter tier. |

Webhook handling is idempotent via a per-billing-record `processedSessions` array, so duplicate webhook deliveries can never double-credit. See [Payments](./payments) for the full lifecycle, customer-portal flow, and the manual-activation fallback for when webhooks fail.

### Marketplace analytics

The backend exposes two analytics endpoints that power the in-app Insights screen and the public homepage stats widget:

- `GET /api/analytics` — per-user insights (interaction summary, cross-app actions, trends). Delegates to the Oxy ecosystem `horizonService` when available, otherwise returns a sensible fallback so the screen always renders.
- `GET /api/analytics/stats` — public marketplace aggregates: total properties, cities, saves, average/min/max rent, top cities, and a price-bucket histogram.

See [Analytics](./analytics) for the aggregation pipelines, the Insights screen wiring, and the fallback behaviour.

### Identity via Oxy

`OxyProvider` from `@oxyhq/services` owns the auth context, account switcher, and the bottom-sheet system. The frontend wires it inside `BloomThemeProvider` (from `@oxyhq/bloom`) and a TanStack `QueryClientProvider` so Homiio's own contexts coexist with Oxy's.

```tsx
<BloomThemeProvider fonts>
  <QueryClientProvider client={queryClient}>
    <RentalModeProvider>
      <OxyProvider baseURL={OXY_BASE_URL}>
        <ProfileProvider>
          <SavedPropertiesProvider>
            <NotificationProvider>
              <BottomSheetProvider>
                {/* ... */}
              </BottomSheetProvider>
            </NotificationProvider>
          </SavedPropertiesProvider>
        </ProfileProvider>
      </OxyProvider>
    </RentalModeProvider>
  </QueryClientProvider>
</BloomThemeProvider>
```

See [Auth](./auth) for the full sign-in lifecycle, profile bootstrap, and the backend `oxy.auth()` middleware.

## Routes at a glance

**Frontend (Expo Router):** `(tabs)` (home, inbox, saved, profile, sindi), `explore`, `properties`, `addresses`, `agency`, `reviews`, `evictions`, `contracts`, `applications`, `landlord`, `viewings`, `reservations`, `stays`, `host`, `exchange`, `roommates`, `agent`, `insights`, `horizon`, `tips`, `settings`, `notifications`, `donate`. **`/search` is a redirect to `/explore` and holds no logic.**

**Backend (Express):** `properties`, `rooms`, `leases`, `applications`, `viewings`, `reservations`, `exchanges`, `roommates`, `reviews`, `addresses`, `evictions`, `partners`, `profiles`, `notifications`, `analytics`, `ai`, `images`, `billing`, `telegram`, `scraper`, plus city, neighborhood, geocoding and observability handlers.
