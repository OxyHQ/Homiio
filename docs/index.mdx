# Homiio

Homiio is the housing trust and transparency layer: find a place, research its history, learn what it really costs, understand what living there was like, and manage or defend the tenancy. The frontend is a single Expo / React Native codebase targeting iOS, Android and Web. The backend is a Node + Express API on PostgreSQL with PostGIS, plus Stripe for subscriptions, Oxy Files for photos and private documents ([Oxy Files](./oxy-files)), and **Sindi**, the housing agent on Alia that the app opens through `@alia.onl/sdk`.

## What it is

More than a listings marketplace, and the difference is structural rather than aspirational:

- **A dwelling is permanent; a listing is temporary.** A listing is a sourced advertisement pointing at a physical place. Reviews, rent history and eviction records attach to the *place*, so they outlive the advert. See the [Glossary](./glossary) and [ADR 0001](./adr/0001-canonical-housing-graph).
- **Location is never implicit — but it is never a toll either.** Every surface that answers "where?" says which area it is querying, free text and geographic scope are separate dimensions, and a geocoding failure is a visible error rather than a silent worldwide feed. Opening the app asks nothing: with no saved area and no granted permission, the server infers a rough area from the visitor's own connection and labels it as a guess, and failing that the app shows named destinations rather than a step to complete. [ADR 0002](./adr/0002-location-and-search-contract) and [Approximate location](./geoip).
- **Privacy by precision.** An address, a coordinate and a review are stored at one precision and published at a coarser one, decided by audience rather than by whichever serializer runs. [ADR 0003](./adr/0003-privacy-verification-publication).
- **Prices must be explainable.** Local, versioned, with their reasoning and confidence — never one universal score. [ADR 0004](./adr/0004-local-explainable-pricing).
- **Tenant–landlord messaging is audited, not assumed.** Allo SDK0.4 and Homiio SDK0.2 are published, and the existing [case-team chat](./team-chat) integration uses resource capabilities, membership and client-held MLS keys. Those APIs do not activate a generic "Message landlord" feature or let a backend create encrypted conversations on a person's behalf. The [messaging audit](./messaging-audit) distinguishes its dated findings from the current integration; the [housing parity matrix](./housing-parity) keeps landlord messaging blocked until its product and encryption requirements are implemented.

- **Parity with Bloom Housing is tracked, not claimed.** [The housing parity matrix](./housing-parity) states, surface by surface, what is live, partial, open, blocked or deliberately divergent — and names the test behind every "live", so a row cannot be closed by shipping JSX or an unreached endpoint.
- **Moderation is communal.** No admin panel, no moderator queue, no privileged action over user content. That is a product decision, not a gap.
- **Beyond rentals.** `PropertyType` covers couchsurfing, co-living, hostels, guesthouses, campsites, boats, treehouses and yurts, each with `accommodationDetails` for sleeping arrangement, host preferences, languages and meals.
- **Canonical organizations.** Agency and housing-support roles reference the Oxy organization directory. Historical labels remain immutable source evidence; unresolved observations are not published as companies. [Architecture and migration](./central-organizations).
- **Identity via Oxy.** Sign-in, account switching and avatars come from `@oxy.so/services`. Homiio stores no passwords.

The four records above are **Proposed**: they bind design, and they are not all shipped. Where this documentation describes a target it says so.

Inside the repo:

| Package | Role |
|---------|------|
| `frontend` (`@homiio/frontend`) | Expo Router app. NativeWind + Tailwind for styling, Zustand for local state, TanStack Query for server state, `@oxy.so/bloom` for primitives. |
| `backend` (`@homiio/backend`) | Express 4 + drizzle-orm (PostgreSQL + PostGIS) API, plus a separate worker process. Stripe billing, photos and private tenancy documents in Oxy Files, BullMQ ingestion, and the capability catalogue Alia and MCP clients call. |
| `listing-providers` (`@homiio/listing-providers`) | The provider plugin contract, the shared fetch runtime, and the portal plugins. Consumed by the worker. |
| `shared-types` (`@homiio/shared-types`) | Pure TypeScript — the entity DTOs, the `format/` money/unit/date module, and the observability event schema. Built first via `postinstall`. |

Build order matters: `@homiio/shared-types` is built ahead of the others via a root `postinstall`, then `frontend` and `backend` can build in parallel.

## Install

```sh
git clone https://github.com/OxyHQ/Homiio.git
cd Homiio
bun install
```

`bun install` resolves all three workspaces and runs `bun run build:shared-types` automatically as `postinstall`.

### Prerequisites

- Node.js 22.x (pinned in `engines`)
- Bun 1.0+
- PostgreSQL with PostGIS (local or hosted)
- For iOS: macOS + Xcode. For Android: Android Studio.

## Core concepts

### Listings and places

A listing (`Property`) is an advertisement; the place it points at is an `addresses` row, and only the place is permanent. A listing carries `id`, an `address`, and **`offerings`** — the single source of truth for how it is offered:

```ts
offerings: OfferingType[];        // long_term_rent | short_term_rent | sale | exchange
longTermRent?: LongTermRent;      // present iff offerings includes LONG_TERM_RENT — monthlyAmount
shortTermRent?: ShortTermRent;    // present iff offerings includes SHORT_TERM_RENT — nightlyRate
sale?: PropertySale;              // present iff offerings includes SALE — price
exchange?: PropertyExchange;      // present iff offerings includes EXCHANGE — swap | host | both
```

The server validates that `offerings` **exactly equals** the set of priced blocks present, and each block's unit is fixed: monthly is always monthly, nightly always nightly, whatever the browse mode.

A listing is either first-party (`oxyUserId` set) or external (`isExternal: true`, no owner, mandatory `sourceUrl`, an `expires_at` deadline reaped by the expiry sweep). External listings are visibly marked and cannot be applied to or booked in-app.

See [Listings](./listings) for the full DTO, the address relation, the filters and external ingest.

### Personal case collaborators

A case keeps its creator as owner. From the case detail, the creator adds an existing Oxy account after confirming that collaborators may edit the case, publish updates and read its exact address. Only the creator manages this team or deletes the case. The team is separate from attendance and from an organization attribution.

The authenticated team endpoint drives the editing controls. Exact location is requested separately, never carried in the public case or public SDK cards, and still requires the household authorization recorded when the case was opened. Removing a collaborator revokes their editing rights and any previous exact-location grant. Reads, edits and team changes serialize on the case row, so a request waiting behind removal rechecks the current membership. Actor-only change records include content edits, team changes, location reads and deletion, without copying address or contact data. The deletion record survives the case.

### Profiles, not users

Homiio sits behind Oxy identity. Each Oxy user gets one or more **profiles** (Personal, Agency, Business, Cooperative). Personal profiles include an auto-calculated trust score from profile completion, verification status, rental history, and references.

The frontend's `ProfileProvider` loads profiles immediately after `useOxy()` reports authentication; the backend's `getOrCreateActiveProfile` endpoint creates a default Personal profile on first sign-in. There's no separate "create your account" step — profile creation is transparent.

### Sindi and Alia

Alia is Homiio's main AI ("Ask Alia"); Sindi, the housing agent, is an ordinary public Alia agent owned by the Homiio project account, and "Ask Sindi" opens the same dialog with Sindi's character (Alia ADR 0020). **Sindi and Alia are reached from the frontend through `@alia.onl/sdk` under the person's Oxy session; Homiio's backend never calls Alia.** The person present pays for the turn with their own Alia credits.

The app mounts the SDK's one sheet (`AliaAskProvider`, `context/AskAgentProvider.tsx`) and nothing else: Sindi has no Homiio-made page, panel or settings. It declares **host tools** — the five things Sindi may do to the screen (`apply_search`, `show_saved`, `open_listing`, `set_results_view`, `navigate`), executed by `hooks/useSindiActions.ts` — sends what the screen shows as the turn's `clientContext`, and draws the catalogue's results with its own **renderers** (`PropertyCard`, saved homes, "which Barcelona?"). Conversations, titles, share links, files and voice are Alia's.

What Sindi can do to the person's Homiio data is the **capability catalogue** (`packages/backend/capabilities/`): 167 tools Alia calls with Oxy capability tickets, bounded by Sindi's published ceiling (Oxy ADR 0042), and the same catalogue serves Homiio's public MCP. Homiio+ unlocks documents through the `sindi.files` feature gate. Homiio never calls Kaana or an inference provider, and holds no provider key.

Detail, and where every former Sindi capability now lives: [Sindi is an Alia agent](./sindi).

### Stripe billing (Homiio+ / file credits / Founder)

Three products are wired through Stripe Checkout:

| Product | Mode | Effect |
|---------|------|--------|
| `plus` | `subscription` | Sets `Billing.plusActive: true`, unlocks unlimited contract reviews and premium features. |
| `file` | `payment` | One-off, increments `Billing.fileCredits` by 1. |
| `founder` | `subscription` | Sets `Billing.founderSupporter: true` — supporter tier. |

Webhook handling is idempotent via a per-billing-record `processedSessions` array, so duplicate webhook deliveries can never double-credit. See [Payments](./payments) for the full lifecycle, customer-portal flow, and the manual-activation fallback for when webhooks fail.

### Marketplace analytics

The backend exposes two analytics endpoints that power the in-app Insights screen and the public homepage stats widget:

- `GET /api/analytics` — per-user insights (interaction summary, cross-app actions, trends). Delegates to the Oxy ecosystem `horizonService` when available, otherwise returns a sensible fallback so the screen always renders.
- `GET /api/analytics/stats` — public marketplace aggregates: total properties, cities, saves, average/min/max rent, top cities, and a price-bucket histogram.

See [Analytics](./analytics) for the aggregation pipelines, the Insights screen wiring, and the fallback behaviour.

### Identity via Oxy

`OxyProvider` from `@oxy.so/services` owns the auth context, account switcher, and the bottom-sheet system. The frontend wires it inside `BloomProvider` (from `@oxy.so/bloom`) and hands it the app's one TanStack `QueryClient`, which `OxyProvider` provides to the whole tree, so Homiio's queries and Oxy's share a cache.

```tsx
<BloomProvider>
  <RentalModeProvider>
    <OxyProvider baseURL={OXY_BASE_URL} clientId={OXY_CLIENT_ID} queryClient={queryClient}>
      <ProfileProvider>
        <SavedPropertiesProvider>
          <NotificationProvider>
            <BottomSheetProvider>
              {/* ... */}
            </BottomSheetProvider>
          </NotificationProvider>
        </SavedPropertiesProvider>
      </ProfileProvider>
    </OxyProvider>
  </RentalModeProvider>
</BloomProvider>
```

See [Auth](./auth) for the full sign-in lifecycle, profile bootstrap, and the backend `oxy.auth()` middleware.

## Routes at a glance

**Frontend (Expo Router):** `(tabs)` (home, inbox, saved, profile, and `sindi/shared/[token]` for a shared conversation), `explore`, `properties`, `addresses`, `agency`, `reviews`, `evictions`, `contracts`, `applications`, `landlord`, `viewings`, `reservations`, `stays`, `host`, `exchange`, `roommates`, `agent`, `insights`, `tips`, `settings`, `notifications`, `donate`. **`/search` is a redirect to `/explore` and holds no logic.**

**Backend (Express):** `properties`, `rooms`, `leases`, `applications`, `viewings`, `reservations`, `exchanges`, `roommates`, `reviews`, `addresses`, `evictions`, `partners`, `profiles`, `notifications`, `analytics`, `ai`, `images`, `billing`, `telegram`, `scraper`, plus city, neighborhood, geocoding and observability handlers.

The complete table — every path, its method, and whether it needs a session — is [Routes](./routes).
