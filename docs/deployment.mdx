# Deployment

The backend deploys to **AWS ECS Fargate** and the frontend web export deploys to a **Cloudflare Worker** with Static Assets. Both are driven by GitHub Actions on push to `main`. ECS task definitions, ALB routing, ECR and SSM secrets are owned by `~/Oxy/oxy-infra/terraform-uswest2/`.

## Backend (AWS ECS Fargate)

Workflow: `.github/workflows/deploy-aws.yml`

- Region `us-west-2`, cluster `oxy-cluster`, service `homiio`, port `4000`, domain `api.homiio.com` (Cloudflare DNS-only → ALB + ACM HTTPS).
- Builds `api` and `worker` `linux/arm64` targets from
  `packages/backend/Dockerfile`, pushes both to ECR
  (`237343248947.dkr.ecr.us-west-2.amazonaws.com/oxy/homiio`), then rolls their
  corresponding ECS services by immutable digest.
- Auth is GitHub OIDC assuming the `oxy-github-deploy` role — no AWS keys are stored in GitHub.
- Secrets: AWS SSM is the ONLY copy (`/oxy/homiio/*`, SecureString; shared ones under `/oxy/_shared/*` are owned by oxy-infra). ECS injects them into the container at task start; the deploy writes none, and GitHub holds no runtime secret. To change one: `aws ssm put-parameter --type SecureString --overwrite --name /oxy/homiio/<NAME> --value '…'`, then force a new deployment of `homiio` (and `homiio-worker` if it reads it). A NEW secret is written to SSM before a task definition names it (oxy-infra runbook 46).
- Listing-ingestion worker: browser-enabled `worker` target from the same
  compiled commit, separate ECS service (`app-homiio-worker.tf` in oxy-infra);
  command runs `packages/backend/dist/worker.js`. The API deploys the `api`
  target, which does not contain Playwright/Chromium/X11.
- Runtimes (since 2026-10): **both targets run on Bun**, from different bases.
  The `api` target is `oven/bun:<packageManager version>-slim` (Debian/glibc,
  `CMD ["bun", "packages/backend/dist/server.js"]` under tini), and the `pre`
  migrator one-shot in `.github/scripts/deploy-ecs-image.sh` runs `bun`. The
  `worker` target keeps `node:22-bookworm-slim` with the pinned bun binary (and
  its `bunx` symlink) copied in, because Playwright's `install --with-deps` and
  its Chromium/X11 packages are installed and proven on that base; the real
  Node left beside bun is what makes a worker rollback a command change. The
  worker's ECS command is declared by the deploy — `TASK_COMMAND_JSON` on the
  worker lane of `deploy-aws.yml`, `xvfb-run … bun
  packages/backend/dist/worker.js` — which replaces the command on every
  revision it registers, because the worker service ignores terraform's
  task-definition changes and a release otherwise carries the live command
  forward. oxy-infra's declaration must agree with it but does not reach the
  running service. The `post` migrator on that lane runs `bun` too. Every
  command must name its own image's runtime: `bun` against a Node-only image
  dies, and `node` against the API image silently runs Bun (the `oven/bun`
  image's `node` is a symlink to bun). `deployMigrationWiring.test.ts` reads
  each target's `CMD` and holds the two migrator commands and the worker's
  command to it.
- Rolling the worker back to Node: change `bun` to `node` in the worker lane's
  `TASK_COMMAND_JSON` and `POST_DEPLOY_TASK_COMMAND_JSON`. The image still
  carries Node, so nothing else changes. Do not plain-revert the change that
  introduced `TASK_COMMAND_JSON` while a bun revision is live: the lane would
  stop declaring a command, carry the live `bun` one forward, and pair it with a
  Node-only image (the circuit breaker would roll that back, and the deploy
  would go red).
- The residential proxy is a runtime-dependent client. `createProxiedFetch`
  uses Bun's native `fetch({ proxy })` under Bun and undici's `ProxyAgent`
  under Node, and the two report a CONNECT refusal differently: Bun throws
  `Proxy refused to open a tunnel: 402 Payment Required` with `status` /
  `statusText` / `headers` fields, and undici buries `Proxy response (402) !==
  200 when HTTP Tunneling` two `cause` levels down. `describeProxyFailure`
  reads Bun's structured `status` first and either wording second, so a 402 is
  `billing` (and fires the `listing-proxy-unusable` alarm in oxy-infra) on
  both. `proxyHealthCheck.test.ts` holds it to recorded fixtures of both shapes
  and to a live local CONNECT proxy, and CI runs it under jest on Node and
  under `bun test`.
- CI's `image-smoke` job builds both targets. `.github/scripts/smoke-api-image.sh`
  runs the deploy's own migrator commands on their lanes' images, `/health` 200
  from the API image's default CMD, Bun under tini, exit 0 on SIGTERM, and a
  non-zero exit when the database is unreachable.
  `.github/scripts/smoke-worker-image.sh` runs the worker image with the
  deploy's own worker command: Playwright launching Chromium headless and
  headed under `xvfb-run` on Bun, a BullMQ boot (against a throwaway Redis)
  with the browser tier loaded, bun under tini and `xvfb-run`, SIGTERM reaching
  the worker and ending in exit 0, and a non-zero exit with no database. The
  backend job also runs the unit suite under `bun test` (`test:bun`).
- `xvfb-run` in the worker image is `packages/backend/scripts/xvfb-run-ready.sh`.
  It is tini's direct child, so it FORWARDS SIGTERM to the worker and waits for
  it: the container's exit code is the worker's own. Before 2026-10 it exited
  143 on the signal and took the container down mid-shutdown.

## Frontend (Cloudflare Worker)

Workflow: `.github/workflows/deploy-frontends.yml`

1. `bun install --frozen-lockfile`
2. Builds `@homiio/shared-types` with `tsc`.
3. Runs `bun run build` in `packages/frontend` (Expo web export to `dist/`).
4. Runs `wrangler deploy` in `packages/frontend`, which uploads `dist/` as the Worker's Static Assets.

Everything the deploy needs is declared in `packages/frontend/wrangler.toml` rather than passed on the command line: the asset directory, the SPA fallback, and `homiio.com` as a custom domain.

This is a **Worker**, not a Pages project, and the difference is the point. A Pages project always serves `<project>.pages.dev` and Cloudflare offers no way to turn that off, which left a second complete copy of the app on a hostname `server.ts` does not allow-list — it rendered the shell and had every API call refused. `workers_dev = false` leaves `homiio.com` as the only name that reaches the deployment.

Two consequences worth knowing before touching this:

- **The apex `homiio.com` must carry no externally managed DNS record.** A Worker custom domain writes its own and refuses a hostname that already has one (`code: 100117`). `api.homiio.com` is a separate hostname pointing at the ALB and is unaffected.
- **`_redirects` and `_headers` are Pages conventions.** SPA routing is `not_found_handling = "single-page-application"` in `wrangler.toml` now; adding those files back to `public/` would only ship them into `dist/` as public assets.

`EXPO_PUBLIC_*` variables are inlined into the bundle at build time. Anything not prefixed will not be visible at runtime.

## Persistent-process vs serverless guards

The backend code still carries guards for serverless runtimes (`process.env.VERCEL`, `AWS_LAMBDA_FUNCTION_NAME`). On ECS neither is set, so the backend runs as a normal long-lived process:

`packages/backend/config.ts` switches the Postgres connection pool sizing automatically:

```ts
maxPoolSize: process.env.VERCEL ? 1 : 10,
serverSelectionTimeoutMS: process.env.VERCEL ? 30000 : 5000,
socketTimeoutMS: process.env.VERCEL ? 60000 : 45000,
bufferCommands: false,
```

`services/cron.ts` is **only** initialised in persistent environments:

```ts
if (!process.env.VERCEL && !process.env.AWS_LAMBDA_FUNCTION_NAME) {
  initCronJobs();
}
```

On ECS this means cron jobs run inside the long-lived service task: health checks, and the expiry sweep that deletes external listings past their `expires_at` (Postgres does not reap them by itself — see `packages/backend/db/expiry.ts`).

## Environment

**Frontend build:**

```
EXPO_PUBLIC_API_URL=https://api.homiio.com
EXPO_PUBLIC_OXY_API_URL=https://api.oxy.so
EXPO_PUBLIC_STRIPE_LINK_PLUS=https://buy.stripe.com/...   # optional
EXPO_PUBLIC_STRIPE_LINK_FILE=https://buy.stripe.com/...   # optional
```

**Backend (SSM and task-definition environment → ECS):**

```
NODE_ENV=production
DATABASE_URL=postgres://...
OXY_API_URL=https://api.oxy.so
STRIPE_SECRET_KEY=sk_live_...
STRIPE_WEBHOOK_SECRET=whsec_...
STRIPE_PRICE_PLUS=price_...
STRIPE_PRICE_FILE=price_...
STRIPE_SUCCESS_URL=https://homiio.com/profile/subscriptions?session_id={CHECKOUT_SESSION_ID}
STRIPE_CANCEL_URL=https://homiio.com/profile/subscriptions
```

Homiio stores no files of its own: photos and private tenancy documents are files in Oxy Files (ADR 0043), and its own S3 bucket was retired on 2026-10-21. [Oxy Files](./oxy-files) has the model, `OXY_FILES_WEBHOOK_SECRET`, and the record of the retirement. Old `/api/images/file/` photo URLs still answer: a 301 to the photo's Oxy rendition, or a 404.

**The API carries no Oxy service credential of its own.** It proves what it is
by attesting its ECS task role and gets a short-lived Oxy service token back
(oxy ADR 0026); `@oxy.so/core` >= 1.6.1 takes that path whenever
`OXY_SERVICE_API_KEY` and `OXY_SERVICE_API_SECRET` are absent. Because a release
renders from the task definition the service is already RUNNING, removing the
pair took an explicit entry in the API lane's `TASK_CONFIGURATION_REMOVALS_JSON`
— deleting the lines that supplied it would have left it inherited forever.

**Sindi and Alia need nothing in this deploy.** The app reaches them through
`@alia.onl/sdk` under the person's Oxy session, and the backend never calls
Alia: there is no chat route, no Alia origin, no agent id and no inference
routing profile in either task definition. Because a release renders from the
task definition the service is already RUNNING, the variables the retired relay
read — `ALIA_API_URL`, `SINDI_ALIA_AGENT_ID`, `OXY_INFERENCE_ROUTING_PROFILE_ID`,
and the older `SINDI_OXY_SERVICE_API_*` pair — are named in both lanes'
`TASK_CONFIGURATION_REMOVALS_JSON`, so an old revision's values are stripped
rather than inherited. The API lane overrides only `OXY_API_URL`.

What Sindi may do on a person's Homiio data is the capability catalogue
(`packages/backend/capabilities/`), which Alia calls with Oxy capability tickets
at `api.homiio.com/_oxy/mcp`; the public MCP is `mcp.homiio.com`
([Sindi](./sindi), [Routes](./routes)). Sindi's agent row, prompt, ceiling and
feature gates live in Alia and are edited in its agent editor, not deployed
from here.

Homiio holds no inference provider key and never addresses Kaana. Provider keys
remain encrypted in Kaana PostgreSQL/KMS and must never be added to Homiio
GitHub secrets, SSM or ECS environment variables.

Dependency versions live only in the package manifests. Publish the contracts
and core changes in dependency order, then run `bun install` here to refresh
`bun.lock` before building Homiio. An older lock/package is not a deployable
substitute and must fail closed rather than be cast to the new request shape.

## CORS

`server.ts` allow-lists `https://homiio.com` and (in dev) `localhost` plus private LAN IPs (RFC 1918). Anything else is rejected. Change the allow-list in `server.ts` if production lands on a new domain.

## Stripe webhook

After deploying the backend, register the webhook endpoint with Stripe pointing at `https://api.homiio.com/api/billing/webhook` and subscribe to:

- `checkout.session.completed`
- `customer.subscription.updated`
- `invoice.payment_succeeded`
- `invoice.payment_failed`
- `customer.subscription.deleted`

Copy the signing secret into `STRIPE_WEBHOOK_SECRET`. Verify the wiring with `GET /api/billing/webhook-test` — it reports which env vars are present and the resolved webhook URL.

## Health checks

- `GET /health` — public, returns `status`, `version`, `environment`, and the PostgreSQL `database` status.
- `GET /api/health` — same shape, mounted under the authenticated tree. Use for smoke-test monitors.
