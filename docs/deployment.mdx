# Deployment

The backend deploys to **AWS ECS Fargate** and the frontend web export deploys to a **Cloudflare Worker** with Static Assets. Both are driven by GitHub Actions on push to `main`. ECS task definitions, ALB routing, ECR, SSM secrets, and the S3 media bucket are owned by `~/Oxy/oxy-infra/terraform-uswest2/`.

## Backend (AWS ECS Fargate)

Workflow: `.github/workflows/deploy-aws.yml`

- Region `us-west-2`, cluster `oxy-cluster`, service `homiio`, port `4000`, domain `api.homiio.com` (Cloudflare DNS-only → ALB + ACM HTTPS).
- Builds `api` and `worker` `linux/arm64` targets from
  `packages/backend/Dockerfile`, pushes both to ECR
  (`237343248947.dkr.ecr.us-west-2.amazonaws.com/oxy/homiio`), then rolls their
  corresponding ECS services by immutable digest.
- Auth is GitHub OIDC assuming the `oxy-github-deploy` role — no AWS keys are stored in GitHub.
- Secrets: AWS SSM is the ONLY copy (`/oxy/homiio/*`, SecureString; shared ones under `/oxy/_shared/*` are owned by oxy-infra). ECS injects them into the container at task start; the deploy writes none, and GitHub holds no runtime secret. To change one: `aws ssm put-parameter --type SecureString --overwrite --name /oxy/homiio/<NAME> --value '…'`, then force a new deployment of `homiio` (and `homiio-worker` if it reads it). A NEW secret is written to SSM before a task definition names it (oxy-infra runbook 46).
- Listing-ingestion worker: browser-enabled `worker` target from the same
  compiled commit, separate ECS service (`app-homiio-worker.tf` in oxy-infra);
  command runs `packages/backend/dist/worker.js`. The API deploys the `api`
  target, which does not contain Playwright/Chromium/X11.
- Runtimes, per target (since 2026-10): the `api` target runs on **Bun**
  (`oven/bun:<packageManager version>-slim`, Debian/glibc, `CMD ["bun",
  "packages/backend/dist/server.js"]` under tini), and the `pre` migrator
  one-shot in `.github/scripts/deploy-ecs-image.sh` runs `bun`. The `worker`
  target stays on **Node** (`node:22-bookworm-slim`, no bun in the image): its
  command lives in the running task definition (`xvfb-run … node
  packages/backend/dist/worker.js`, from oxy-infra and carried forward by every
  deploy, since the worker service ignores terraform task-definition changes),
  and the `post` migrator in `deploy-aws.yml` runs `node` on that image. Every
  command must name its own image's runtime: `bun` against the worker image
  dies, and `node` against the API image silently runs Bun (the `oven/bun`
  image's `node` is a symlink to bun). `deployMigrationWiring.test.ts` reads
  each target's `CMD` and holds the two migrator commands to it.
- Why the worker is not on Bun yet, measured 2026-10-12: Playwright 1.61.1
  launches headless and headed (Xvfb) Chromium under Bun, but the residential
  proxy path is runtime-dependent. Under Bun, `createProxiedFetch` uses Bun's
  native `fetch` `proxy` option instead of undici's `ProxyAgent`, and a proxy
  refusing CONNECT with 402 surfaces as `Proxy refused to open a tunnel: 402
  Payment Required`, which `describeProxyFailure` does not parse. The proxy
  check then reports `network` instead of `billing`, so the
  `listing-proxy-unusable` alarm (oxy-infra) would never fire for the outage it
  exists for. Moving the worker needs that classification fixed, the proxied
  fetch path proven on the real proxy, the worker image to ship bun, and only
  then the worker command switched (in the deploy, since terraform no longer
  reaches the running revision).
- CI's `image-smoke` job builds both targets and runs
  `.github/scripts/smoke-api-image.sh`: the deploy's own migrator commands on
  their lanes' images, `/health` 200 from the API image's default CMD, Bun under
  tini, exit 0 on SIGTERM, and a non-zero exit when the database is
  unreachable. The backend job also runs the unit suite under `bun test`
  (`test:bun`).

## Frontend (Cloudflare Worker)

Workflow: `.github/workflows/deploy-frontends.yml`

1. `bun install --frozen-lockfile`
2. Builds `@homiio/shared-types` with `tsc`.
3. Runs `bun run build` in `packages/frontend` (Expo web export to `dist/`).
4. Runs `wrangler deploy` in `packages/frontend`, which uploads `dist/` as the Worker's Static Assets.

Everything the deploy needs is declared in `packages/frontend/wrangler.toml` rather than passed on the command line: the asset directory, the SPA fallback, and `homiio.com` as a custom domain.

This is a **Worker**, not a Pages project, and the difference is the point. A Pages project always serves `<project>.pages.dev` and Cloudflare offers no way to turn that off, which left a second complete copy of the app on a hostname `server.ts` does not allow-list — it rendered the shell and had every API call refused. `workers_dev = false` leaves `homiio.com` as the only name that reaches the deployment.

Two consequences worth knowing before touching this:

- **The apex `homiio.com` must carry no externally managed DNS record.** A Worker custom domain writes its own and refuses a hostname that already has one (`code: 100117`). `api.homiio.com` is a separate hostname pointing at the ALB and is unaffected.
- **`_redirects` and `_headers` are Pages conventions.** SPA routing is `not_found_handling = "single-page-application"` in `wrangler.toml` now; adding those files back to `public/` would only ship them into `dist/` as public assets.

`EXPO_PUBLIC_*` variables are inlined into the bundle at build time. Anything not prefixed will not be visible at runtime.

## Persistent-process vs serverless guards

The backend code still carries guards for serverless runtimes (`process.env.VERCEL`, `AWS_LAMBDA_FUNCTION_NAME`). On ECS neither is set, so the backend runs as a normal long-lived process:

`packages/backend/config.ts` switches the Postgres connection pool sizing automatically:

```ts
maxPoolSize: process.env.VERCEL ? 1 : 10,
serverSelectionTimeoutMS: process.env.VERCEL ? 30000 : 5000,
socketTimeoutMS: process.env.VERCEL ? 60000 : 45000,
bufferCommands: false,
```

`services/cron.ts` is **only** initialised in persistent environments:

```ts
if (!process.env.VERCEL && !process.env.AWS_LAMBDA_FUNCTION_NAME) {
  initCronJobs();
}
```

On ECS this means cron jobs run inside the long-lived service task: health checks, and the expiry sweep that deletes external listings past their `expires_at` (Postgres does not reap them by itself — see `packages/backend/db/expiry.ts`).

**Backend (SSM and task-definition environment → ECS):**

```
NODE_ENV=production
DATABASE_URL=postgres://...
OXY_API_URL=https://api.oxy.so
STRIPE_SECRET_KEY=sk_live_...
STRIPE_WEBHOOK_SECRET=whsec_...
STRIPE_PRICE_PLUS=price_...
STRIPE_PRICE_FILE=price_...
STRIPE_SUCCESS_URL=https://homiio.com/profile/subscriptions?session_id={CHECKOUT_SESSION_ID}
STRIPE_CANCEL_URL=https://homiio.com/profile/subscriptions
OXY_INFERENCE_ROUTING_PROFILE_ID=01a06477-94f5-74f0-bc25-4c5c13b93ccd
ALIA_API_URL=https://api.alia.onl
SINDI_ALIA_AGENT_ID=01a0646a-078f-7514-9800-9f43ceed7df8
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_REGION=us-west-2
AWS_S3_BUCKET=oxy-homiio-media-usw2-237343248947
```

Production uses native AWS S3 — omit `AWS_ENDPOINT_URL`. The bucket name and region are set in `~/Oxy/oxy-infra/terraform-uswest2/app-services.tf`.

**The API carries no Oxy service credential of its own.** It proves what it is
by attesting its ECS task role and gets a short-lived Oxy service token back
(oxy ADR 0026); `@oxy.so/core` >= 1.6.1 takes that path whenever
`OXY_SERVICE_API_KEY` and `OXY_SERVICE_API_SECRET` are absent. Because a release
renders from the task definition the service is already RUNNING, removing the
pair took an explicit entry in the API lane's `TASK_CONFIGURATION_REMOVALS_JSON`
— deleting the lines that supplied it would have left it inherited forever.

**Sindi carries no key pair either.** Sindi is the same attested task role:
Oxy's Sindi entry point admits only the handle derived from `oxy-homiio-task`
(`wl_f28159178c5e993eb03b8cc1`), and the backend's Sindi client is constructed
with no credential at all. The `SINDI_OXY_SERVICE_API_*` pair and its credential
`01a0648e-ad3f-7608-aa8b-c07bfef6cf73` are retired; the backend no longer reads
those variables, and the deploy keeps stripping them from both task
definitions in case an old revision still carries them.
`SINDI_ALIA_AGENT_ID` and `OXY_INFERENCE_ROUTING_PROFILE_ID` are non-secret GitHub
repository **variables** copied byte-for-byte into only the API task definition.
The deploy refuses a missing/malformed value and never discovers an agent or
profile by slug/display name, list position or fallback. The routing value is
the exact opaque primary key returned by the catalogue bootstrap. The deploy
also pins `ALIA_API_URL=https://api.alia.onl` instead of inheriting an arbitrary
value from an older task revision. The listing worker receives none of these
inference settings, including either API origin.

These are Oxy identity/routing values, not upstream provider credentials. All
provider keys remain encrypted in Kaana PostgreSQL/KMS and must never be added
to Homiio GitHub secrets, SSM or ECS environment variables. Kaana's only
canonical signed origin is `https://kaana.ai`; Homiio never addresses it
directly or through an `oxy.so` alias.

The reserved Oxy desired state names the other Sindi identities: project account
`6a50444ce8026582b949089d`, bot account
`01a0646a-078f-7974-9645-a5e8be237f47`, service application
`6a2f851751b784a86fd0e922`, and its task role
`arn:aws:iam::237343248947:role/oxy-homiio-task`. After apply, the agent must be private, its
`oxyAccountId` is the bot account, and its capability grant is exactly `web`.
These are opaque primary keys, never names or list positions; no public Homiio
request may create or rebind them. These are not assertions about current live
state: require provisioner apply and byte-exact readback of every relation.

Dependency versions live only in the package manifests. Publish the contracts
and core changes in dependency order, then run `bun install` here to refresh
`bun.lock` before building Homiio. An older lock/package is not a deployable
substitute and must fail closed rather than be cast to the new request shape.

Sindi chat needs no user consent: each turn carries a requester assertion Oxy
mints from the signed-in user's live session (OxyHQServices ADR 0025), so the
backend never returns `SERVICE_ACTING_AS_UNAUTHORIZED` for chat. Deploy order is
Oxy (mint + introspection), then Alia (accepts the assertion), then Homiio.
The OAuth reconsent path below is kept for a future absent-user feature using
`inference:invoke acting-as:offline`: the frontend may offer that action only
after a backend returns exact code `SERVICE_ACTING_AS_UNAUTHORIZED`, and may
retry only after Oxy reports `consented`. Web uses exact redirect
`https://homiio.com`; native uses exact redirect `homiio://oauth/consent` with
the SDK-owned state and PKCE flow. Until the `@oxy.so/services` release exposing
`requestOAuthConsent` is present in the manifest and lockfile, the UI remains
fail-closed and production is not deployable.

This section describes the reviewed target, not the current production task.
Neither a merged Homiio branch nor values present in Oxy's database prove that
the two service credentials reached SSM, that the live Homiio API received the
exact agent/profile IDs, or that either request path completed. Follow
`~/Oxy/oxy-infra/docs/runbooks/39-homiio-inference-runtime.md` and require the
live task-definition readback plus both application canaries before calling the
cutover complete.

## CORS

`server.ts` allow-lists `https://homiio.com` and (in dev) `localhost` plus private LAN IPs (RFC 1918). Anything else is rejected. Change the allow-list in `server.ts` if production lands on a new domain.

## Stripe webhook

After deploying the backend, register the webhook endpoint with Stripe pointing at `https://api.homiio.com/api/billing/webhook` and subscribe to:

- `checkout.session.completed`
- `customer.subscription.updated`
- `invoice.payment_succeeded`
- `invoice.payment_failed`
- `customer.subscription.deleted`

Copy the signing secret into `STRIPE_WEBHOOK_SECRET`. Verify the wiring with `GET /api/billing/webhook-test` — it reports which env vars are present and the resolved webhook URL.

## Health checks

- `GET /health` — public, returns `status`, `version`, `environment`, and the PostgreSQL `database` status.
- `GET /api/health` — same shape, mounted under the authenticated tree. Use for smoke-test monitors.
