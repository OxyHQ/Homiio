# Deployment

The backend deploys to **AWS ECS Fargate** and the frontend web export deploys to **Cloudflare Pages**. Both are driven by GitHub Actions on push to `main`. Homiio does **not** deploy to DigitalOcean App Platform or droplets — ECS task definitions, ALB routing, ECR, SSM secrets, and the S3 media bucket are owned by `~/Oxy/oxy-infra/terraform-uswest2/`.

## Backend (AWS ECS Fargate)

Workflow: `.github/workflows/deploy-aws.yml`

- Region `us-west-2`, cluster `oxy-cluster`, service `homiio`, port `4000`, domain `api.homiio.com` (Cloudflare DNS-only → ALB + ACM HTTPS).
- Builds `api` and `worker` `linux/arm64` targets from
  `packages/backend/Dockerfile`, pushes both to ECR
  (`237343248947.dkr.ecr.us-west-2.amazonaws.com/oxy/homiio`), then rolls their
  corresponding ECS services by immutable digest.
- Auth is GitHub OIDC assuming the `oxy-github-deploy` role — no AWS keys are stored in GitHub.
- Secrets: GitHub Actions secrets are the source of truth. The workflow syncs them to AWS SSM (`/oxy/homiio/*`; shared secrets to `/oxy/_shared/*`) and ECS injects them into the container. To change a secret, edit it in GitHub — the next deploy applies it.
- Listing-ingestion worker: browser-enabled `worker` target from the same
  compiled commit, separate ECS service (`app-homiio-worker.tf` in oxy-infra);
  command runs `packages/backend/dist/worker.js`. The API deploys the `api`
  target, which does not contain Playwright/Chromium/X11.

## Frontend (Cloudflare Pages)

Workflow: `.github/workflows/deploy-frontends.yml`

1. `bun install --frozen-lockfile`
2. Builds `@homiio/shared-types` with `tsc`.
3. Runs `bun run build` in `packages/frontend` (Expo web export to `dist/`).
4. Deploys `packages/frontend/dist` with `wrangler pages deploy` to the `homiio-frontend` Pages project.

`EXPO_PUBLIC_*` variables are inlined into the bundle at build time. Anything not prefixed will not be visible at runtime.

## Persistent-process vs serverless guards

The backend code still carries guards for serverless runtimes (`process.env.VERCEL`, `AWS_LAMBDA_FUNCTION_NAME`). On ECS neither is set, so the backend runs as a normal long-lived process:

`packages/backend/config.ts` switches the Postgres connection pool sizing automatically:

```ts
maxPoolSize: process.env.VERCEL ? 1 : 10,
serverSelectionTimeoutMS: process.env.VERCEL ? 30000 : 5000,
socketTimeoutMS: process.env.VERCEL ? 60000 : 45000,
bufferCommands: false,
```

`services/cron.ts` is **only** initialised in persistent environments:

```ts
if (!process.env.VERCEL && !process.env.AWS_LAMBDA_FUNCTION_NAME) {
  initCronJobs();
}
```

On ECS this means cron jobs run inside the long-lived service task: health checks, and the expiry sweep that deletes external listings past their `expires_at` (Postgres does not reap them by itself — see `packages/backend/db/expiry.ts`).

Production uses native AWS S3 — omit `AWS_ENDPOINT_URL`. The bucket name and region are set in `~/Oxy/oxy-infra/terraform-uswest2/app-services.tf`.

The point-inference `OXY_SERVICE_API_*` pair and Sindi's separate
`SINDI_OXY_SERVICE_API_*` pair are written directly to the exact
`/oxy/homiio/` SSM SecureStrings by Oxy's exact-application-ID credential
provisioner. They are not Homiio GitHub secrets; deploy only verifies those
parameters without decryption before using their exact ARNs.
`SINDI_ALIA_AGENT_ID` and `OXY_INFERENCE_ROUTING_PROFILE_ID` are non-secret GitHub
repository **variables** copied byte-for-byte into only the API task definition.
The deploy refuses a missing/malformed value and never discovers an agent or
profile by slug/display name, list position or fallback. The routing value is
the exact opaque primary key returned by the catalogue bootstrap. The deploy
also pins `ALIA_API_URL=https://api.alia.onl` instead of inheriting an arbitrary
value from an older task revision. The listing worker receives none of these
eight inference settings, including either API origin.

These are Oxy identity/routing values, not upstream provider credentials. All
provider keys remain encrypted in Kaana PostgreSQL/KMS and must never be added
to Homiio GitHub secrets, SSM or ECS environment variables. Kaana's only
canonical signed origin is `https://kaana.ai`; Homiio never addresses it
directly or through an `oxy.so` alias.

Oxy's internal bootstrap owns the other Sindi identities: project account
`01a0646a-078f-72ea-8759-86326484a7e0`, bot account
`01a0646a-078f-7974-9645-a5e8be237f47`, service application
`6a2f851751b784a86fd0e922`, and service credential
`01a0648e-ad3f-7608-aa8b-c07bfef6cf73`. The agent is private, its
`oxyAccountId` is the bot account, and its capability grant is exactly `web`.
These are opaque primary keys, never names or list positions; no public Homiio
request may create or rebind them.

The exact-ID client field ships additively in `@oxyhq/core@23.2.0`, backed by
`@oxyhq/contracts@0.40.0`. Publish contracts first and core second, then run
`bun install` here to refresh `bun.lock` before building Homiio. The manifests
already require those versions; an older lock/package is not a deployable
substitute and must fail closed rather than be cast to the new request shape.

This section describes the reviewed target, not the current production task.
Neither a merged Homiio branch nor values present in Oxy's database prove that
the two service credentials reached SSM, that the live Homiio API received the
exact agent/profile IDs, or that either request path completed. Follow
`~/Oxy/oxy-infra/docs/runbooks/39-homiio-inference-runtime.md` and require the
live task-definition readback plus both application canaries before calling the
cutover complete.

## CORS

`server.ts` allow-lists `https://homiio.com` and (in dev) `localhost` plus private LAN IPs (RFC 1918). Anything else is rejected. Change the allow-list in `server.ts` if production lands on a new domain.

## Stripe webhook

After deploying the backend, register the webhook endpoint with Stripe pointing at `https://api.homiio.com/api/billing/webhook` and subscribe to:

- `checkout.session.completed`
- `customer.subscription.updated`
- `invoice.payment_succeeded`
- `invoice.payment_failed`
- `customer.subscription.deleted`

Copy the signing secret into `STRIPE_WEBHOOK_SECRET`. Verify the wiring with `GET /api/billing/webhook-test` — it reports which env vars are present and the resolved webhook URL.

## Health checks

- `GET /health` — public, returns `status`, `version`, `environment`, and the PostgreSQL `database` status.
- `GET /api/health` — same shape, mounted under the authenticated tree. Use for smoke-test monitors.
