# Routes

Generated by reading `packages/backend/routes/` and `packages/frontend/app/`, and
kept honest by `bun run check:docs`, which fails when a mounted router or a
top-level frontend segment is missing from this page.

Re-derive it rather than trusting it:

```bash
# Backend: every route, multiline-safe. A line-based grep MISSES most of them,
# because the path usually sits on the line after `router.post(`.
for f in packages/backend/routes/*.ts; do
  echo "### $(basename "$f" .ts)"
  perl -0777 -ne 'while (/router\s*\.\s*(get|post|put|patch|delete)\s*\(\s*["\x27]([^"\x27]*)["\x27]/gs) { print "  $1 $2\n" }' "$f" | sort -u
done

# Frontend: every screen.
git ls-files -- packages/frontend/app/ | sed 's|packages/frontend/app/||' | sort
```

## How auth is decided

**By which router a handler is mounted on, not by a check inside it.**

```
app.use('/api', publicRoutes());                              # no session required
app.use('/api', createOxyAuthMiddleware(oxy), routes());      # 401 without one
```

Both are mounted at `/api`; the public router is first, so a path it declares is
served before the authenticated router is reached. `optionalAuth` runs globally
*before* both, so a public handler can still see a signed-in viewer when one is
present — which is how an eviction's `isAttending` resolves without making the
board private.

Two consequences:

- **Moving a handler between `routes/public.ts` and `routes/index.ts` changes its
  auth requirement silently.** There is no per-handler annotation that would go
  red.
- **A handler on the public router must never read `req.user` for
  authorization.** It may read it to personalise a response. If the answer
  depends on who is asking, the handler belongs on the authenticated router.

### Home

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/home/sections` | The whole Home surface in one request, under ONE scope |

`loc` is the scope and it is a single atomic token (ADR 0002 §5.1), not a set of
geographic parameters — a half-updated scope is unrepresentable in the request as
well as in the store. Three answers are deliberately distinct and a client must
render them differently: **no `loc`** is answered everywhere with
`location.status: "none"`; an **unreadable** `loc` is a **400**, never a global
page; and a `loc` naming a place that does not resolve is a `200` carrying
`location.status: "unresolved"` and no sections at all.

`loc=here.<radiusMeters>` carries no coordinates by design, so a device scope
sends `lat` and `lng` beside it — in the request only, never in the echo, a key
or a log.

## Known gap: viewing creation is not mounted

`packages/frontend/services/viewingService.ts` calls
`POST /api/properties/:propertyId/viewings` and
`GET /api/properties/:propertyId/viewings`. **Neither path is registered on any
router.** `viewingController.createViewingRequest` exists and is unreachable.

Measured on this branch, with a positive control so "found nothing" is
distinguishable from "the search is broken":

```bash
grep -rn "propertyId/viewings\|createViewingRequest" packages/backend/routes/   # → nothing
grep -rn "mark-transacted" packages/backend/routes/                              # → 1 hit, so the search works
```

Recorded here rather than quietly omitted: a route table that lists only what
exists would leave the next person to rediscover this from a 404. Approving,
declining and cancelling a viewing all work; only creating one is missing.

### `/search` → `/explore`, unambiguously

The discovery experience lives at **`/explore`**. `/search` is a
backward-compatibility redirect and holds no logic, no filters and no data
fetching.

| Old path | Redirects to | Mechanism |
|---|---|---|
| `/search` | `/explore` | `<Redirect href="/explore" />` |
| `/search/<query>` | `/explore/<query>` | reads the `query` segment; falls back to `/explore` when absent |

Query-string parameters survive both, because they live on the URL rather than
the path: `/search?offering=short_term_rent` lands on
`/explore?offering=short_term_rent`.

**Never add a screen, a filter, a hook or a data fetch under `/search`.** It goes
in `/explore`. The redirect exists for links, bookmarks and deep links that
predate the move, and for nothing else.

`typedRoutes` does **not** protect you here: on this expo-router major a
`router.push` to a route that does not exist type-checks clean. Verify a route
move by grepping for every old route string **and** loading the route in a real
browser, including the negative case.

## Response contracts

Every `/api` body is built by `middlewares/errorHandler.ts` and passed through
`middlewares/wireIds.ts`.

**Every identity is `id`** and never `_id`.

### Success

```json
{
  "success": true,
  "message": "Operation successful",
  "data": {},
  "meta": { "timestamp": "2026-08-10T12:34:56.000Z" }
}
```

### Paginated

`paginationResponse` adds a `pagination` block beside `data`:

```json
{
  "success": true,
  "message": "Success",
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 137,
    "totalPages": 7,
    "hasNext": true,
    "hasPrev": false,
    "nextPage": 2,
    "prevPage": null
  },
  "meta": { "timestamp": "2026-08-10T12:34:56.000Z" }
}
```

`GET /api/properties/search` and `cityController.getPropertiesByCity`
additionally expose **flat aliases** — `total`, `page`, `limit`, `totalPages`,
`hasMore` — beside the nested block, because the infinite-scroll hooks read them
directly. That duplication is deliberate; it keeps `normalizeEnvelope` on the
frontend intact. New list endpoints feeding an infinite grid should do the same.

Note `hasMore` and `hasNext` are computed differently: `hasNext` is
`page < totalPages`, while `hasMore` is `(page - 1) * limit + data.length < total`,
which accounts for a short final page.

### Errors

```json
{
  "success": false,
  "error": { "message": "…", "code": "…", "statusCode": 400 }
}
```

`AppError(message, statusCode, code)` is how a handler raises one; `asyncHandler`
forwards to the single `errorHandler`, which is the only place that decides what
a caller sees. A handler must not build its own error body.

### Geographic error codes

| Code | Status | Raised when |
|---|---|---|
| `MISSING_PARAMETERS` | 400 | `lat`/`lon` absent on reverse geocoding, or `q` absent on forward |
| `INVALID_COORDINATES` | 400 | `lat`/`lon` present but not parseable as numbers |
| `GEOCODING_FAILED` | 502 | the upstream geocoder failed or returned nothing usable |
| `OFFERING_VALIDATION_ERROR` | 400 | `offerings` does not exactly match the priced blocks present |

**A geocoding failure is an error a person can see.** It must never degrade into
an unscoped, worldwide result set — that is invariant 4 of
[ADR 0002](./adr/0002-location-and-search-contract), and the failure it exists to
prevent is a map of Madrid over a list of homes in Barcelona.

**Target, not current:** the typed location-error vocabulary, the server-side
geocoding gateway that removes the frontend's direct calls to a public geocoder,
and the `LocationSelection` echo on every search response are ADR 0002 with
issues #351, #295 and #352. Today the frontend still calls Nominatim directly
from `hooks/useAddressSearch.ts`, alongside the backend `/api/geocoding/*`
endpoints above.
